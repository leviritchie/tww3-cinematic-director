# Cinematic Director (Total War: WARHAMMER III mod)

Cinematic action camera for battles, a cinematic HUD, and Unicorn Overlord-style unit tactics edited in the campaign (player orders are locked in battle; units follow their tactics).

## Layout
- `script/_lib/mod/` - shared: `cinematic_director_ui.lua` (UI kit `CD_UI`), `cinematic_director_tactics_catalog.lua` (conditions/targets/actions/plays/presets/paradigms, `CD_TACTICS`), `cinematic_director_abilities.lua` (ability keys by category, `CD_ABILITIES`)
- `script/campaign/mod/cinematic_director_tactics.lua` - campaign tactics editor; exports `cinematic_director_tactics.txt` in the game folder before battles
- `script/battle/mod/` - `cinematic_director.lua` (camera director), `cinematic_director_hud.lua` (HUD), `cinematic_director_tactics.lua` (tactics engine), `cinematic_director_tactics_panel.lua` (battle tactics panel + paradigm buttons + deployment editor), `cinematic_director_probe.lua` (banner probe experiment, off: `ENABLED` at the top)
- `ui/templates/cd_*.twui.xml` + `ui/skins/default/cinematic_director/*.png` - generated by `python tools/make_ui.py` (edit the generator, not the XML)
- `docs/workshop_description.txt` - Steam Workshop text (BBCode); `cinematic_director.png` - Workshop preview
- `_reference/vanilla_script/` - extracted vanilla scripts for API lookups (not packed, not ours)
- `retired/`, `*_backup.lua.txt` - old versions, not packed

## Build and install
```
python build_pack.py
cp cinematic_director.pack "/v/SteamLibrary/steamapps/common/Total War WARHAMMER III/data/"
```
Only `script/` and `ui/` go into the pack.

## Testing
The game takes a long time to load: verify offline in the LOVE harness before asking for an in-game test.
```
cd tools/harness
CD_MOD="V:/games/TWW3 Cinematic Director/" timeout 120 "/c/Program Files/LOVE/lovec.exe" .                 # campaign editor flow
CD_MOD="V:/games/TWW3 Cinematic Director/" CD_SCN=battle timeout 180 "/c/Program Files/LOVE/lovec.exe" .   # battle: tactics, panel, director, HUD
```
Battle harness checks for the above: `CHECK brace cam` (a second wolf unit gallops into the crossbowmen from behind at tick 470), `CHECK heavy hits filmed` (forced hp drops at ticks 700/746, the first after a cast), `CHECK slow motion` (the mock's `SPEED` scales movement and damage; each period 1.8-2.4 s, speed back to 1; MP run: `CHECK no slow motion in multiplayer`), `CHECK unit cards` (fake `battle_orders > cards_panel` at y 910/930: banner and callouts above it, priority 1402 then restored); renders `d1_action_hit`, `d2_brace`; `CD_TRACE_ACT=1`, `CD_TRACE_WOLF=1` print each tick.
`CD_SCN=plays` runs a small battle through the engine only and checks each play (cycle charge phases, hammer wait/swing/rear/hit, kiting, focus fire, high ground, fire support) and paradigm switching; every `CHECK` line should say yes.
`CD_SCN=fights` runs three fixed melees (losing badly, winning, even) and checks fight states, the fight conditions, the fight targets, and rows/spells using "Enemy/Ally from WHEN".
`CD_SCN=deploy` edits a unit's rows in the battle panel during deployment (paradigm I and II) and checks the battle uses them: `CHECK set up during deployment`, `deployment editing`, `paradigm editing`, `battle uses the edits`, `no edits in battle`, `paradigm II used`; renders `e1_deploy_picker`, `e2_deploy_row`, `e3_deploy_paradigm2`.
The battle run also checks `CHECK unit card hover` (render `b8_card_hover`), `CHECK unit card hover (states)`, `CHECK unit card click while filming`, and `CHECK banner probe` when the probe is on. The deploy run checks `CHECK clicks from button states`. `CHECK heavy hits filmed` occasionally says no for "yours" (unseeded randomness in the run); rerun before chasing it.
`CD_SCN=hammer CD_HC=left|right|front|far` runs a static engaged line (5 v 5, reserve behind theirs) with one unit per hammer variant starting from that spot, and prints a `ROUTE` line each: time to the charge, angle off the target's rear, path length, closest other enemy passed.
`CD_SCN=hunt CD_HC=left|right|front|far|centre` runs the same engaged line with archers behind it and three Hunt missiles units (cavalry, infantry, missile cavalry), printing a `HUNT` line each: target reached, time, path, closest enemy troops passed (should stay >= 40 m; the straight charge went through the line at 5-12 m). `CD_TRACE=<unit key>` prints its positions.
Options: `CD_CANCEL=1` (released units drop orders), `CD_MP=1` (multiplayer battle). Renders go to `%APPDATA%/LOVE/cdh4/*.png`; the harness writes its own `cinematic_director_log.txt`.

In game: `<game>/cinematic_director_log.txt` (full log; the director logs each subject pick with its top candidates and why, e.g. `pick: *giant 14.2/14.2 [melee, kills 3.0/s, duel]`). The game's own `lua_mod_log.txt` shows script loading; crash dumps are in `%APPDATA%/The Creative Assembly/Warhammer3/crash_report`.

## Game scripting gotchas learned the hard way
- The game runs Lua 5.1: no `goto`, no integer division operator.
- UI components created hidden and shown later never appeared; create visible, then hide/show.
- Place screen-level panels with `core:get_screen_resolution()` + `MoveTo`; the UI root's `Bounds()` grows with its children in battle.
- Never create a `script_ai_planner` for player units: it keeps them AI-controlled (greyed, unselectable). Issue direct orders, then `release_control()`; the unit keeps the order.
- Multiplayer (untested in game): the tactics engine turns itself off in `watch()` (`bm:is_multiplayer()`, the same call slow motion uses), so no setup, orders or lock; harness `CD_MP=1` checks `CHECK no unit tactics in multiplayer`. The campaign editor has no multiplayer guard: the one added in the Workshop pass (`cm:is_multiplayer()` in build()) was a suspect in the campaign crash, so it stays out until it can be tested in game. The Workshop text says so.
- The log (`cinematic_director_log.txt`) is started afresh when the director loads and it is over 4 MB.

- Wrap every callback the game calls (listeners, first tick, timers) in pcall. Vanilla runs first-tick callbacks in a plain loop (`call_each`, no pcall), so one error skips everything queued after it.
- Campaign: never call methods on an event context, and never build or redraw UI inside a game event. Listeners only record what happened (`context.string` is a plain field and is fine); the work runs from our repeating 100 ms watch timer (`cm:repeat_real_callback`). A one-shot `cm:real_callback(f, 1)` never fired in game; 0 runs immediately, still inside the event. Read the selected army from vanilla's `cm.campaign_ui_manager.mf_selected_cqi`.

## Crash analysis tools
Crash dumps (`.mdmp`) can be read offline with small Python scripts (pefile + capstone are installed):
- exception address: Warhammer3.exe's real code section is the first section (section names are scrambled)
- binding names: find `lea` references to the crashing function; the strings nearby name the Lua method
- the dump holds the lua_State (crashing binding's `rsi`) and the Lua value stack, but not closures or CallInfo, so Lua source lines can't be recovered

## Tactics model
- A row is `{cond, target, action}`, saved as `c,t,a;...`. Movement rows: first row whose condition holds, target exists and play doesn't decline wins; nothing applies -> attack nearest. Spell rows run separately (`cast_pass`).
- Conditions return `true, unit1, unit2` when they are about units (the closest one found; e.g. `ally_losing` -> the ally and its foe, `lord_in_melee` -> lord and foe, `under_fire` -> nearest enemy shooter). Targets `trigger_enemy`/`trigger_ally` ("Enemy/Ally from WHEN") take the first of those of their side; none -> no target, row skipped. `choose()` and `cast_pass`/`try_cast` pass them to `TARGET[id](me, t1, t2)`; `near()` returns `true, unit`.
- Fight states (`fight_states` in `snapshot`): each unit's health loss per second (`loss_rate`, share of the unit, smoothed ~6 s) against the average of enemies in melee within 40 m. `r.fight` = lose_bad (>= 2.5x theirs and > 0.6%/s, or wavering) / win_big (mirror, or a foe wavering) / lose / win (1.5x and > 0.3%/s); `r.foe` = nearest of them. Computed for both sides. Conditions self_winning(_big), self_losing(_bad), ally_winning, ally_losing(_bad) (150 m; category "Fights"); targets enemy_winning_fight, enemy_losing_fight, ally_losing_fight. The game's own verdict overrides the estimate's direction where readable (`native_fight`): the unit's strongest morale effect via `common.get_context_value("CcoBattleUnit", tostring(unit:unique_ui_id()), "MoraleGreatestEffect")` (vanilla reaches unit contexts the same way), compared with the localised `random_localisation_strings_string_unit_encouraged_winning` ("Winning current combat") / `..._unit_concerned_losing` ("Losing currently"), [[col]] tags stripped; read at most once a second per unit. No Lua unit method exposes it; the engine has a 7-step state (`land_combatant_{losing,winning}{_big,,_slightly}`, `land_combatant_even`) and morale kv `winning_combat(_slightly/_significantly)`, `losing_combat(_significantly)`, but scripts can only see the top morale line. `fight probe:` log lines (every 5 s, up to 4 units in melee) print the estimate next to the context values (MoraleGreatestEffect, StatusMostImportant.Key, StatusColour, PercentHpLostRecently, DamageInflictedRecently, MoraleState, MoralePercent) for tuning; unverified in game.
- Plays (`T.PLAYS`) are compound one-row behaviours with per-unit state `e.st`: hammer (+ hammer_flank, hammer_wide), cycle_charge, skirmish, focus, fire_support, disrupt, kill_lord, high_ground, duelist, caster. Plays marked `passes` decline (fall to the next row) when they have nothing to do.
- Hammer routing (`HAMMER` table in the engine: `arc` = how far off straight behind it may start its charge, `berth` = extra width): the rear is away from the nearest of our units fighting the target, blended with the army's facing. The unit goes straight to the tangent of a circle round the target (clear of its neighbours in line, `hammer_radius`), then along it, on the shorter side (`hammer_side`; sticks unless the other becomes 30% shorter). Target = engaged enemy with the shortest route, +80 m per enemy screening its rear. It charges at `arc`, in melee, or after the route's expected time x1.6 (min 45 s).
- Hunt missiles (`disrupt`) goes round enemy troops in the way (`detour` in the engine): enemies other than the target and shooters are circles `DETOUR_R` (40 m); if the straight way crosses one, the wall of circles linked to it (`DETOUR_LINK` 90 m) is gone round on the shorter side by heading just past its edge, re-planned each tick (phase `round`). A circle the unit is already inside shrinks to its distance so it doesn't spiral in. Missile units only detour while over 170 m from the target.
- Help and preset texts (`T.HELP`, preset descriptions) say what the unit does, concisely, in plain words: no rationale or strategy advice, and no jargon ("hammer the line", "kite", "flank", "buff", "exposed"). Play names may be referred to by name.
- Preset ids share names with actions (hammer, focus, skirmish): never regex-replace catalog entries by id alone.
- Deployment editing: the engine's `watch` runs `setup` during deployment (`prepare`, `E.prepared`; `deploying()`), so the battle panel can edit rows before the fight via `set_rows(e, k, rows)` (refused once running). Editing paradigm I rebinds unsaved II-IV (same table) to the new rows. `start()` skips `setup` when prepared; orders lock only at start. The panel: click a unit, a row (`cd_bt_rowb_i`), its cells `cd_bt_cell_c/a/t`, then a category/option in the picker `cd_bt_pick` (`cd_bt_pcat_j`, `cd_bt_opt_k`) left of the card; the paradigm strip picks the set shown (`P.edit_k`). Edits last for this battle only (not written back to the campaign).
- Lords and heroes always get `T.MAX_SLOTS`. Own spells: `sp_<abilitykey>` actions; the engine writes the abilities each character can cast to `cinematic_director_spells.txt` (`spells <unit cqi> key ...`), which the editor's "Own spells" group reads.
- Paradigms: up to 4 tactics sets per unit (save keys `<cqi>` for I, `<cqi>p<k>` for II-IV; an unsaved paradigm copies I). Export: `force <cqi> <general rank>`, `unit ...`, `para <idx> <k> <rows>`. Unlocks by the highest rank among the player's living generals in the battle (`T.PARADIGM_RANKS` = 1/5/12/20); all generals dead or routing locks switching. 20 s cooldown between shifts (`CFG.paradigm_cooldown`). Units whose rows are the same in both paradigms carry on undisturbed.

## Camera model (director)
- The director starts by itself when deployment ends (`CFG.auto_start`, polled every 500 ms); the hotkeys still toggle it. The HUD starts in letterbox mode (`H.mode = "film"`), and unit banners are hidden while filming (`hide_banners`). The unit cards stay on screen while filming (`CFG.show_unit_cards`: `hide_ui` skips `show_army_panel`): the HUD raises `battle_orders` to priority 1402 over the letterbox bar (its own `Priority()` restored when the HUD turns off), puts the banner in the top bar in film mode (above the cards otherwise), and keeps callouts above the top of `battle_orders > cards_panel` (read once a second; fallback 14% of the screen height).
- Player's view: `battle.home` (your army -> enemy, from the first survey) is fixed for the battle. `home_view()` bends every shot's camera round its look point to within `home_max_dev` (soft, tanh) of it, then raises it to look down at least `min_pitch`. Volleys are filmed from the player's side (behind your shooters, or behind your regiment under fire).
- Speeds are halved (`max_cam_speed` 17.5 m/s); glides are capped at `blend_speed_mult` x that, so long glides take longer (up to `glide_max`). On a glide the camera locks onto the new shot's (unsmoothed) look point as it travels, turning at `glide_turn_mult` x the normal rate, so the subject is seen early; it never looks down more than `glide_max_pitch` (an earlier version carried the destination view along, which stared at the ground mid-glide). Glides accelerate at `blend_accel_mult` x `max_cam_accel` and swoop up only a little (`swoop_lift`/`swoop_max`).
- Close charge cam (`SHOTS.charge_close`, `close_camera()`), the one exception to the limits: when cavalry, a chariot or a monster (big, class `^mon`; not `cav_mis`) is `close_charge_ttc` (1.8 s) from hitting something weak to its charge (`charges_well`: not monsters, cavalry, characters or anything big; spears/pikes (`unit_class` with spr/pik) only when already fighting or hit from the side/behind), it cuts in (no glide, no focus hold if the current shot is >= 1.5 s old or on one of the two) 9-12 m behind and beside the riders, 2.3-3 m up, nearly level, fov `close_charge_fov`. It follows the riders' raw position with an alpha-beta filter (no smoothing lag, no speed limit, no home_view, no min_pitch), brakes to a stop when they touch (gap < contact_radius+4 or melee; the ttc estimate is often early, so it's only a +1.5 s backstop), watches `close_charge_after` (2 s), then glides to an `impact` shot of the pair. 20 s cooldown. When your troops are the ones charged it is the brace cam instead (`SHOTS.charge_brace`, same `close_camera()` with rider/other swapped): 8-11 m behind your unit (away from the charger), 2-2.6 m up, looking at the charger's filtered position (4 m up if big) until the hit. Both are `direct` shots: code that means "the close cams" tests `SHOTS[t].direct`, not the type name. Candidates come from detect_events' charge check (`note_close_charge`, ours and shooters first). Harness: `CHECK close charge matchups`, `CLOSE #n` lines (camera behind/beside/height/pitch, its speed vs the riders'); `CD_GALLOP=1` makes cavalry ride at 18 m/s, `CD_TRACE_CLOSE=1` prints each tick.
- Action shots (`CFG.action_*`, off with `action_shots`): a unit losing `action_hit` (0.06; `action_hit_big` 0.08) unary hp within `action_window` (1.5 s) while out of melee (not in melee for 3 s, no enemy within 20 m) gets a `hit` event (`add_hit`, 20 s per unit): source = a cast on it in the last 4 s (`cd.cast_on`, from `CD_DIRECTOR_NOTIFY`) -> "hit by a spell from X"; else `find_shooter` -> "bombarded by" (artillery) / "riddled by"; else an enemy lord/hero out of melee within 260 m -> "hit by a spell"; else "hit hard". It is always a highlight, skips the pair/unit cooldowns, is `urgent` (ready at once), expires after `action_ttl` (5 s, per-event `e.ttl`), and cuts in after `action_hold` (1 s, even mid-glide; off a highlight after `action_hl_hold` 3.5 s). `SHOTS.action_hit` (cut_in): 12-16 m (16-22 big) from the unit, 25-50 deg off the line of fire, 2.4-3.4 m up, behind your unit / in front of an enemy one, looking at it; `sh.min_pitch = action_pitch` (7) replaces `min_pitch` in `home_view`. A highlight shot isn't widened while it plays (`min_focus_hold`).
- Slow motion (`CFG.slow_mo*`): `slow_mo(why)` sets `bm:modify_battle_speed(0.3)` for `slow_mo_len` (2 real s, ended from the tick by `slow_mo_end`), 10 s cooldown; skipped in multiplayer, when paused or already below 1x. It restores the saved speed only if the speed is still ours (the player may have changed it); while paused it waits. Triggered at the close/brace cam's hit, at an action_hit cut if the hit is <= 1 s old (else on the shot's next hit >= 2x `hit_threshold`, `sh.slow_on_hit`), and on highlight shots of charges/rear/side hits at their first hit >= `hit_threshold` within impact_t + 2.5 s (`slow_hit_mult`, `slow_until`). Director off restores it. Unknown: whether the engine runs `camera:move_to` durations in game time (the camera is nearly still while slowed).
- Highlights (`highlight_of(kind, a, b)`, `CFG.highlight_*`, off with `CFG.highlights`): events clearly good or bad for the player. They are a charge that `charges_well`, a rear hit, a side hit by cavalry or a big unit, shooters/artillery (`is_shooter`: class `^art` or `mis`, or ranged and not cavalry) caught in melee by non-shooters, a unit breaking, and a general badly hurt (new `hurt` event: in melee below `hurt_hp`). The event gets `e.hl` (+`highlight_bonus` score) and is filmed alone and close (`highlight_scale`; charge_follow/impact for charges, over_shoulder/impact otherwise, heroic for hurt), never grouped or used to widen another shot. It may cut in after `highlight_min_hold` (2.5 s) instead of the usual holds, but nothing cuts a highlight shot (or the close charge cam) before `min_focus_hold`. A highlight's rank grows while it waits (+0.8/s), so queued ones are filmed in turn. The same line isn't filmed again within `highlight_repeat` (40 s); one that expires logs `highlight not filmed`. The close charge cam's reason is the highlight too. HUD: `reason.highlight` -> a bigger box (`HL_*`: 20 pt `hud_name` text, tinted `green_bg`/`red_bg` fill `_tint` under the content, 5 px underline and 4 px leader lines in green/red, cream icon). Harness: `CHECK highlight classes`, `HIGHLIGHT #n` lines, renders `c3_highlight_good`/`c3_highlight_bad`, and `c4_highlight_bad_forced` (a red box forced at tick 600).
- `min_focus_hold` (7 s): nothing takes the camera off a shot sooner (only a lost subject does). Events wait (`event_ttl` 14 s, `volley_ttl` 9 s); a late charge is announced as a clash. The next most important event within `multi_event_radius` is framed in the same wide shot, and the banner names both.
- Battle harness prints `view: N% within 60 deg of the player's view, mean pitch, max speed outside cuts` and `BADVIEW` samples (low pitch or facing away), with the shot type.
- No general check-in shots (`lord_anchor` = 0) and no "your general" focus: an idle general gets no interest bonus (the 1.8x applies only when fighting, shooting or under fire).
- Callouts (HUD): each reason carries its `unit`; the HUD shows a box (`cd_card`, ~92% opaque) over that unit with a leader line in the tone colour down to its head, one per event line (`reason.extra`; up to 4 boxes, `CO_N` / `MAX_LINES`). Every box names one event: never summarise as "and N more" (the player can't expand it). Widening a shot keeps the lines already on screen (`group_reason(heads, group, prev)`), and an event joining an ongoing clash shot adds its own line; harness `CHECK no 'and N more' lines`, stacking/sliding so boxes never overlap; hidden while the unit is behind the camera. Boxes stay still (text moving at the timer's rate, not the camera's frame rate, was hard to read): only the leader line follows the unit, as a drop from the box edge plus a horizontal run (`_hline`) to it; a box jumps to a new spot only when its unit drifts past `CO_DRIFT_X`/`CO_DRIFT_Y`, at most once per `CO_MIN_HOLD` (harness: boxes move on ~5% of ticks). Text wraps to 2-3 lines (`callout_size`: 1 line up to 30 chars, 2 up to 64, else 3; width estimated from `CHAR_W`, height `CO_H` + `CO_LINE` a line). Lines about no unit (overview) keep the bottom banner. Anchored callouts (`CO_ANCHOR`, 2026-10-12, unverified in game): when the unit has a banner on screen (`unit_id_holder > <unique_ui_id>`, `VisibleFromRoot`) and its heads are in the picture, its box is made inside that banner (`cd_hud_ab_<uid>` + `_tint/_icon/_text/_ul/_line`, looked up fresh each tick since the game may remake banners), so the engine moves it every frame. It hangs centred on the banner with its bottom at the banner's bottom (above it when banners are shown); the 40 ms timer only sets its stacking lift (`dy`, held `CO_MIN_HOLD` unless overlapping), edge clamps and the leader line (box child, down to the projected heads). In game the banner (48x75) sat centred on the unit, its bottom ~57 px above the heads at normal range (150-230 px in close shots). Other units keep the projected boxes below. Logs: `callout box made in the banner of ...`, `anchored callout ...: banner x,y, heads project to ...` (every 2 s per box, 60 lines max), `no banner on screen`. Harness banners follow their units (all but the giant), `anchored callout box-ticks N`. Projected boxes: placement runs on its own 40 ms real timer and projects through `CD_DIRECTOR.camera()`, a model of the engine camera: every filming `move_to` goes through `cam_move`, which records start/goal/duration so the camera's position, look point and fov can be evaluated at any clock time (straight-line glide over the move's duration, as assumed elsewhere). Projection: look-at, the `fov` passed to `move_to` taken as vertical (the shaders use `g_vertical_fov`), +x is screen-right when looking along +z (left-handed; vanilla Tamurkhan/Grom scripts' left/right comments agree). Harness prints `callouts: ... line tip off the unit by N px` (independent projection through the mock engine camera) and renders `c1_callout`/`c2_callouts_multi`.
- The battle tactics panel shows in the regular view after a unit is clicked, and while filming when the mouse is over a unit card (placed above that card). Cards are `cards_panel > review_DY > <card>`; a card's `GetContextObjectId("CcoBattleUnit")` is its unit's `unique_ui_id`. `ComponentMouseOn` finds the card (ancestor under `review_DY`); `ComponentMouseOff` clears it on the next panel tick unless an "on" follows. The paradigm strip stays.
- Battle UI input (in game, 2026-10-12): `ComponentLClickUp` never arrived for the tactics panel's components (rows, cells, prev/next, paradigm buttons), though their hover looks changed; it does for the HUD's top-level buttons. `ComponentMouseOn` never arrived while filming. So the panel also reads clicks from button states (`poll_clicks`, 50 ms: `down`/`selected_down` then `hover`/`selected_hover`/`selected` = a click; the same id from the other route within 0.4 s counts once) and the hovered unit card from the card states (`poll_cards`: a card or child state containing "hover"; else one containing "selected"), plus the unit selection callback while filming (click a card -> its tactics card above it until deselected). Real card path: `battle_orders > battle_orders_pane > card_panel_docker > cards_panel > review_DY > <card id = unit unique_ui_id>`, card context `CcoBattleUnit` = the uid. Logs: `click <id> (event|state)`, `click event:`, `mouse-over event:`, `card state:`, `selection:`. Unverified in game.
- Banner probe (`cinematic_director_probe.lua`, experiment, now off): in game a box parented to the unit's banner component `unit_id_holder > <uid>` (placed at 0,-40) stayed visible and followed the unit while filming with `enable_unit_ids(false)` (phase B) - a way to have the engine move callouts every frame. The engine camera (`cam:position()`/`target()`) matched the director's model within ~0.3-5.5 m mean (7.6 m max, up to 12 deg). Original description: tries a box inside `unit_id_holder > <uid> > script_ping_parent` (where vanilla's ping icons go) so the engine would move callouts every frame. Phases: B filming with banners hidden, C filming with banners on but their parts hidden (restored after), A regular view; logs `[probe]` lines each second (box position vs the unit's projection).

## Battle API notes
- `camera:move_to(pos, target, duration, false, fov)`: fov 0 means the game default, whose real value is unknown (vanilla uses 40, 45 and 50). The director always passes an explicit FOV while filming, so it never flips between the two.
- `bm:enable_unit_ids(bool)` shows/hides the floating unit banners (vanilla cutscenes use it).
- Battle unit methods confirmed in the exe: `number_of_enemies_killed`, `current_target`, `is_wavering`, `is_rear_flank_threatened`, `is_left_flank_threatened`, `is_right_flank_threatened`, `is_currently_flying`, `unary_hitpoints`. There is no `is_charging` or `is_firing`.

## Campaign crash (resolved 2026-10-11)
Every build from the 2026-10-09 "Workshop pass" crashed the game when a campaign army was selected. The crash was a null read in the native `context:character()`. Reverting to the exact pre-pass build fixed it: `builds/prepass_2026-10-09/` holds that build, and `script/` is now based on it. The pass changed only the shared logger (CD_LOG) and a `cm:is_multiplayer()` call in the editor's build(); which of the two caused it was never isolated. The pass's work, including the v5 editor, is parked in `retired/v5_after_workshop_pass/`. Re-adding those features is deferred; add them back one at a time, with an in-game test after each.
